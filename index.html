Case study 1 — Interface research and design

Designing a centralized status view for a safety-critical monitoring tool

A safety-critical monitoring tool used to track device output levels across a workspace. Users could check overall output but had no centralized way to monitor individual device status, identify threshold violations, or respond quickly.

Cognitive task analysis SME interviews Alert lifecycle modeling Collaborative prototyping Usability testing Eye-tracking evaluation
Research question
How can users maintain situational awareness of all devices and outputs within a space — and how can their supervisors maintain awareness across all spaces?
Method
Cognitive task analysis and SME interviews to understand user decision-making around threshold violations; development of a device alert lifecycle model; collaborative prototyping with UX design; usability testing with representative users across iterations; eye-tracking evaluation to validate visual salience of active alerts.
Key insight
Interviews revealed two distinct user types with different goals — an in-area user needing device-level specifics to resolve an issue, and a supervisor monitoring multiple areas who mainly needs to know if/when a threshold is crossed. The alert lifecycle model also surfaced that part of the resolution workflow happens outside the software entirely, a reminder to account for the environment around the product, not just the interface itself.
Impact
After 4–5 design iterations, delivered a "device status board" mockup with interaction notes and design rationale, implemented in a subsequent software release with tailored views per user type (role-based access controls to automate that tailoring in progress). In continuous field use since early 2025, and has since prompted follow-on research into other safety-critical monitoring displays and cross-role status sharing among supervisors.
Case study 2 — Requirements & acquisition input

Evaluating a self-service software installation workflow

Long-term subcontractor support to a program transitioning from engineer-led, in-person software installations to a self-service model, intended to support a faster development tempo and reduce reliance on traveling systems engineers.

Document analysis Workflow mapping Contextual inquiry / field observation Survey research HSI reporting
Research question
Does the new installation method define a user-friendly workflow for retrieving, installing, and configuring the software and its auxiliary components — one that end users can complete without engineer support?
Method
Document analysis of the installation guide to map the intended workflow (steps, decisions, inputs, required resources); field observation of a live installation and training session, annotating deviations and troubleshooting; supplementary surveys capturing user demographics and ease-of-use feedback.
Key insight
The documented process had gaps that engineers had to fill in real time, indicating typical users could not install independently as designed. Deeper analysis of the user population — high turnover, most users in-role under two years — surfaced a structural risk: single-admin access control meant the one person with install/config knowledge was likely to leave before transferring it.
Impact
Delivered as an HSI report to program leadership (associate PM, lead engineer, lead trainer, product owner). Installation documentation was revised to close the gaps, and engineers began logging a shared troubleshooting reference now bundled into the install package. The turnover/knowledge-loss finding also prompted new, standardized post-install training requirements — now adopted program-wide.
Case study 3 — Role and permissions validation

Validating user roles ahead of a new capability rollout

A planning and awareness tool with three unit-level user roles and one supervisory group-level role, undergoing program changes that would introduce new capabilities for the group-level user.

Documentation review Permissions matrix development Persona-based workflow mapping User interviews Interoperability analysis Survey research
Research question
Are the existing permissions and capabilities sufficient to support the group-level user's tasking — including the capabilities planned for future releases?
Method
Documentation review to build a role/permissions matrix; persona-based workflow mapping against real-world processes; group-level user interviews validating current responsibilities and future capability plans; discussion of unit-group interoperability; surveys on perceived usability, utility, and satisfaction.
Key insight
Existing permissions largely aligned with group-level needs, but no read-only role existed for users needing visibility without modification rights. More significantly, far less information flowed between unit- and group-level users than assumed: unit-level users track what/where/when within their area, while group-level users only need visibility when something goes wrong site-wide. The tool had been over-provisioning detail to group-level users, most of whom weren't using it — confirming the interface was unit-workflow-centric and underdeveloped for the group-level role.
Impact
Recommendation to add a read-only role was accepted and adopted immediately. The broader finding reshaped the program roadmap to prioritize group-level needs going forward. The role/permissions matrix itself was embedded in the software as a reference and continues to be used in user engagements and training today.
